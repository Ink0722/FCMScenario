# 配额随机分配

工作空间中的独立入口为“配额随机分配”，原来的“测试码与发放”继续用于给一组人安排相同任务。两个入口分别保存流程和历史；配额方案在批次页通过“查看配额方案”返回原安排。

## 使用

1. 按 case 填写 Neutral / Goal 的任务份数，0 表示不分配；可统一填充后逐项修改。
2. 设置每人任务数、整批模型、可选批次名称、最大对话轮数和北京时间到期时间。默认不使用模型。高级选项可指定随机种子。
3. 生成预览，检查每个 case 的计划数、实际分配数、序位分布和逐人任务顺序。此时方案已保存，但不创建参与者和测试码，也不调用模型。
4. 确认后一次性发放，随时从历史打开、查看当前测试码或导出 CSV。重试同一方案不会重复创建参与者；换码后方案页和导出返回当前码。
5. “复制为新方案”预填配额、每人任务数和对话轮数，批次名称追加“副本”，清空到期时间和随机种子；如原方案使用真实模型，必须重新选择模型或明确选择不使用模型。确认新预览时读取当前材料与模型配置，原方案不受影响。复制页可刷新恢复来源，并有未保存离开提醒。
6. 未发放方案可确认删除，删除后不能访问或发放。已发放方案可归档，在历史的“已归档方案”中查看、复制、导出或恢复。归档仅整理配额列表，不撤销测试码、不停止参与，也不隐藏参与记录和批次统计。

配额是计划发放的任务数量，并非保证获得的有效完成样本数。已发放、已完成分别统计；退出或取消不会自动释放配额、补发或改动原方案。当前真实 Advisor 尚未接入，选择真实模型可保存预览，不能发放。

## 约束与分配

Neutral、Goal 分别计算。设该组任务配额总和为 T、每人任务数为 k，则该组人数为 T/k。T 必须能被 k 整除，每个 case 的该组配额不能大于该组人数。每人条件一致、恰好 k 个任务，同人不重复 case。k 为 1–20，单项配额为 0–1000，整份方案最多 1000 人。任何约束不成立均返回原因，不静默降低配额或调整人数。

算法版本 `balanced-load-edge-colour-ab-v2` 先构造满足行列配额的二分分配，通过保度交换打散组合，再用二分图边着色安排任务序位。每个 case 在同一条件下，各序位上的次数差至多 1。

目标 A/B 与展示顺序 AB/BA 也在每个 case、每种条件内分别均衡，数量差各至多 1，四种交叉组合的数量差同样至多 1。余数随机决定，随机结果在预览时固定；不增加 A/B 配额输入。新版均衡只作用于新方案，已保存的 `balanced-load-edge-colour-v1` 方案按原始结果读取和发放，不补改旧安排。上述目标规则仍属于开发规则，正式研究目标尚需审核。

“随机分布检查”展示每个 case、每种条件下的目标、展示与交叉组合数量，并以矩阵显示同一人同时分到两个 case 的人数。旧方案按其原始数据计算，不宣称符合新版均衡。组合随机化不承诺对所有可行分配进行等概率抽样，也不保证所有 case 对共现次数相等；不等配额下共现次数不同可以是配额本身导致。

参与者按固定的随机顺序完成任务，后续任务逐项解锁；服务端同时阻止跳序开始。刷新、退出重做和换码保留原分配顺序。原发码入口保留自由选任务的行为。

同一算法版本、配额、每人任务数和种子可重现相同安排。预览还冻结当时材料、整批模型、目标和选项顺序。方案保存后不就地编辑；需要调整时创建新方案，已发放数据仍归属于原方案。

## API 与持久化

以下接口使用现有管理认证；Cookie 写操作还需 CSRF：

| 方法与路径（前缀 `/api/v1/admin`） | 输入与行为 |
| --- | --- |
| POST `/allocation-plans` | `{requestId,quotas:[{caseId:"01",neutral:20,goal:20}],tasksPerPerson,maxTurns,modelId?,batchId?,expiresAt?,seed?}`；配额数组不能重复 case，返回持久化预览 |
| GET `/allocation-plans?page=1&pageSize=20&archived=false` | 分页返回当前已保存预览和发放历史；`archived=true` 仅返回归档方案，删除方案不返回 |
| GET `/allocation-plans/{planRef}` | 原方案、逐人安排、当前测试码、配额/序位/A/B 核对、共现次数、完成数、归档及可发放状态；含复制所需配额和轮数 |
| POST `/allocation-plans/{planRef}/issue` | `{requestId}`；一次性发放，任意重试返回同批参与者及当前测试码 |
| POST `/allocation-plans/{planRef}/archive` 或 `/restore` | `{requestId}`；已发放方案归档或从归档恢复，保留原发放与访问 |
| POST `/allocation-plans/{planRef}/delete` | `{requestId}`；删除未发放方案，拒绝删除已发放方案 |
| GET `/allocation-plans/{planRef}/export` | 带 BOM 的 CSV，每行一项任务，含位置、条件、目标、选项顺序及当前测试码；未发放时码列为空 |

预览按 requestId 和正文摘要防重，同编号不同正文拒绝。发放同时按请求编号和方案编号防重；同请求编号不能跨方案使用。已过期的未发放方案禁止发放，已发放方案重试可读取原结果。原 `/codes` 接口拒绝配额配置，避免绕过配额和固定顺序。

归档、恢复和删除同样防重并审计，同操作编号不能跨方案或动作复用；重试已完成动作返回原结果，不覆盖后续动作（例如归档后恢复，再重试原归档请求不会重新归档）。删除采用逻辑删除，保留审计、命令防重和不可变工件；列表和访问接口不再提供该方案，重试删除可恢复成功结果。删除与发放共享事务锁，避免并发生成被隐藏的参与者。

无需新增数据库表或迁移：不可变工件保存完整分配和冻结配置；`system_jobs` 登记方案、发放消费和命令防重；个人任务的 `task_data.allocation` 保存序位、方案引用及分配位，独立于可重置的运行状态。SQLite 使用现有写事务，PostgreSQL 使用事务级 advisory lock；本机验收基于 SQLite，未把该结果视作 PostgreSQL 实例上的并发验收。

参与者共享 DTO `TestTask` 增加可选 `sequence`。配额任务列表按该序位返回，未解锁任务公开状态为 `unavailable`；原任务省略该字段。直接跳序开始返回 `409 task_order_locked`。
